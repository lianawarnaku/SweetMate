# Local reliability checks

Run from the canonical repository while its isolated Supabase QA stack is running.
These scripts never read production credentials or accept a remote database URL.
They use the named `supabase_db_sweetmate-qa` container and loopback 54321/54322.

```sh
pnpm run typecheck
pnpm --filter @workspace/mobile run test
node scripts/reliability/run-local-sql.mjs
npm install --prefix /tmp/sweetmate-reliability-tools --no-audit --no-fund pg@8.16.3
node scripts/reliability/test-local-database.mjs /tmp/sweetmate-reliability-tools/node_modules
node scripts/reliability/test-local-services.mjs
node scripts/reliability/test-local-pagination.mjs
node scripts/accounts/test-deletion-client.mjs
node scripts/accounts/test-deletion-runtime.mjs
```

The SQL runner requires each suite to use BEGIN/ROLLBACK. The independent-session
script creates unique disposable users/households, tests real locks and lifecycle
operations, and removes those fixtures in finally. The service script uses real
local Auth tokens, REST and Realtime and deletes only the new accounts it created.
No payment is transferred; financial rows are dummy bookkeeping records.

The service script locates the existing cached macOS Supabase CLI. Override
`SWEETMATE_QA_BACKEND` for a different local QA backend directory if necessary;
its status must still identify `http://127.0.0.1:54321`.

Apply the canonical pending migrations to this local backend before testing.
Do not run these scripts against production, reset an existing QA database, or
publish the private fixture files generated by an optional browser preview.

See `docs/qa/reliability-audit-2026-11-26.md` for failures, fixes, results and limits.

The pagination suite creates 1257-row disposable collections and more than 1000
fixture memberships, verifies the actual local 1000-row response cap and full
ordered reads, tests RLS boundaries, then removes its own users/households. It
never adds production fixtures. See `docs/qa/pagination-2026-11-27.md` for live
production-setting evidence, coverage and limits.


## Durable saves and process termination

`node scripts/reliability/test-durable-termination.mjs` uses the named local QA
Supabase stack, creates disposable accounts, runs each mutation through two
SIGKILL checkpoints, checks receipt replay, and cleans up its fixtures. It must
never be pointed at production. The helper reads local CLI status privately;
credentials are not logged or put in the operation journal.

`node scripts/reliability/test-durable-provider-termination.mjs` runs the actual
feedback/Calendar handlers over loopback with fake upstream services. It does
not contact Google or send email. Both scripts use
`durable-operation-worker.mjs` to create fresh persistence-engine processes.

These process checks do not substitute for force-quitting an installed native
app. See `docs/qa/durable-saves-2026-11-27.md` for the exact matrix and limits.


## Removed-member invitations and abuse controls

`node scripts/reliability/test-household-invitations.mjs` requires local migrations
`202611270001` and `202611270002` plus earlier prerequisites. It creates verified
and unverified disposable Auth accounts and exercises actual local PostgREST/RLS
admission, removal, recipient/host checks, expiry/revocation, concurrent requests,
rate counters, rollback/batch attempts, receipt replay and membership caps.
It never sends an invitation, email, push or message. It removes only its own
accounts/households in `finally`; transactional cap fixtures are rolled back.
The named local database and loopback API are mandatory. Do not run this against
production or reset the shared QA stack. See
`docs/qa/household-invitations-2026-11-27.md` for results and remaining device checks.
